# Предложение: UX-редизайн веб-клиента todoer

Дата: 2026-10-03.

Статус: зафиксированное направление и интерактивный прототип; изменения ещё не перенесены в приложение. Иерархия project → task → subtask сохранена. Продолжение в Local Codex 2026-10-03 завершило остальные экраны и Vue-референсы; DOM, статические проверки и Vue compile/typecheck прошли. Полная браузерная приёмка новых экранов и интеграция с core остаются отдельными шагами.

## Цель и ориентиры

Редизайн охватывает UX, а не только замену темы Nuxt UI. Приложением должно быть удобно и приятно пользоваться: быстро записывать задачи, планировать работу, читать список, перемещать карточки и редактировать детали без потери контекста.

Ориентиры, подтверждённые пользователем: Todoist, Things 3 и OmniFocus. Используем их подходы к быстрому добавлению, спокойной организации ежедневной работы и сохранённым представлениям, сохраняя модель todoer и собственную визуальную систему.

Исходные материалы: [DESIGN.md](../design/DESIGN.md), [tokens.css](../design/tokens.css) и [workflow Open Design](../design/open-design/README.md).

## Визуальное направление

- Нейтральная палитра zinc; indigo обозначает интерактивность, выбор и фокус.
- Системный шрифт, светлая и тёмная темы, английский и русский интерфейсы.
- Название задачи имеет главный визуальный приоритет; метаданные вторичны.
- Плотность не должна ухудшать чтение и попадание по контролам. Длинные названия переносятся; дополнительные строки получают нужную высоту.
- Управление доступно с клавиатуры; действия, скрытые до наведения, также показываются при фокусе. На телефоне обязательные действия доступны без hover.

## Навигация и режимы

Основные входы: «Все открытые», «Сегодня», «Предстоящие», проекты и сохранённые представления. «Все открытые» не переименовывается во «Входящие»: это другой смысл фильтра.

«Сегодня» и «Предстоящие» используют пресеты существующих дат. В прототипе «Сегодня» означает scheduled или due не позднее текущего дня, включая просроченные; «Предстоящие» — любую из этих дат после текущего дня без верхней границы. Задача с датами по обе стороны сегодняшнего дня может входить в оба пресета. Счётчики считают уникальные открытые задачи по одному фильтру, включая свернутых детей. Прототип фиксирует дату 2026-10-03; приложение должно использовать локальную дату с пересчётом при смене дня. Переключение представления не меняет данные задач; создание в этих пресетах не подставляет дату молча.

Переключатель **List / Kanban / Calendar** находится **в правом верхнем углу верхней панели страницы**, по аналогии с read/edit mode в Obsidian. По замечанию пользователя 2026-10-03 Calendar — третий режим в той же группе, с тем же оформлением и поведением; отдельный вход в рабочей навигации не нужен. Это компактные иконки с заметным активным состоянием, подсказками, локализованными доступными названиями и клавиатурным фокусом. Под заголовком дублирующего переключателя нет. Смена режима сохраняет текущий фильтр и данные.

Календарь подключён к общим задачам и drawer, с разными scheduled/due placements. Перенос повторяющегося вхождения моделируется локальной копией без due и собственного RRULE, с Undo без изменения правила серии. DOM-проверки переноса, Undo и закрытых/пропущенных вхождений прошли; это fixture-проверки, не интеграция с core. На узких экранах календарь переходит в список дней с полными датами.

## Быстрое добавление и детали

Добавление начинается с названия. Доступны явное действие «Добавить задачу» и Enter; проект, теги, приоритет и даты раскрываются по мере необходимости. Сохраняется синтаксис todoer `#project @tag pN`; `p0` — самый высокий, `p4` — самый низкий приоритет. Нельзя обещать распознавание естественного языка, которого нет в приложении.

Ошибка не очищает введённый текст. Новая задача становится видна в соответствующем списке или колонке.

Детали открываются в общей боковой панели поверх списка или доски. Название и заметки идут первыми, дополнительные поля раскрываются постепенно. Две даты имеют разные роли:

- **Когда делать** → scheduled date: запланированный день работы.
- **Крайний срок** → due date: дата, к которой задача должна быть завершена.

Сохраняется сохранение полей при потере фокуса, с ненавязчивой обратной связью и понятным сообщением при отказе. Закрытие панели возвращает фокус и контекст исходного элемента. Подзадачи и повторение доступны в деталях.

## Канбан

Канбан — полноценная часть предложения, связанная со списком общими задачами и общей панелью деталей.

- Колонки отражают пользовательские статусы; в демонстрации используются Todo, Doing и Done, причём Done — завершающая колонка.
- Карточки показывают название, важные метаданные, даты, повторение и связь с родителем. Длинные названия переносятся.
- Можно добавить задачу в открытую колонку, открыть детали, перенести карточку между колонками и изменить порядок.
- Для drag-and-drop есть клавиатурные альтернативы: Move to, Move up и Move down.
- Завершение и перемещение дают обратную связь и Undo там, где операция обратима.
- Управление колонками включает переименование, порядок, выбор завершающей колонки и удаление с подтверждением перераспределения задач.
- На телефоне доска прокручивается горизонтально, сохраняя читаемую ширину карточек и доступность действий.

Пустая доска, пустая колонка, ожидание первой синхронизации, offline, очередь записей, отказ и восстановление должны быть проверены отдельно. Галерея этих состояний не загромождает основной рабочий экран.

## Иерархия project → task → subtask

Пользователь задал ориентир поведения: иерархия Jira **epic → story → task**, сопоставленная в todoer как **project → task → subtask**. Это продуктовый ориентир, а не требование переносить весь функционал Jira.

Принятые правила, реализованные в прототипе:

- В списке подзадачи раскрываются внутри родительской задачи; проект объединяет задачи верхнего уровня.
- На доске подзадача может быть отдельной карточкой со своим статусом и явной ссылкой на родительскую задачу.
- Родитель показывает число завершённых детей и общее число подзадач; создание, завершение и Undo сразу обновляют прогресс.
- Подзадача открывается из родителя, а из неё можно перейти обратно к родителю. Поддерживается один уровень подзадач.
- При создании подзадачи подставляется проект родителя. Это начальное значение при создании, а не постоянное наследование: последующие изменения проекта не каскадируются.
- Фильтры сохраняют понятный контекст связи. Ребёнок показывается самостоятельно, когда соответствует фильтру; раскрытие родителя позволяет найти и детей вне фильтра без скрытого изменения их данных.
- Не должно быть неоднозначных дубликатов одной подзадачи и двойного подсчёта задач.
- Завершение подзадачи обновляет прогресс родителя; родитель завершается отдельным действием. Это соответствует проверенным операциям core: завершение не каскадируется между родителем и детьми; подзадача не имеет собственного правила повторения.

Прототип группирует задачи по проектам, включая «Без проекта». Совпавшие с фильтром дети вложены в совпавшего родителя один раз; если родитель исключён, ребёнок показывается в своём проекте со ссылкой на родителя. Дети другого проекта сохраняют свою принадлежность. Сворачивание не меняет счётчики; контекстные ссылки на исключённых детей не входят в них. Прогресс родителя вычисляется по всем прямым детям.

По отчёту Local Codex прошли проверки вложенности, сворачивания, уникальных счётчиков, фильтров «Сегодня» / «Предстоящие» / проекта, создания, независимых изменений проекта, завершения и Undo, отдельных карточек на доске и доступности новых контролов в двух темах и языках. Ограничение fixture: завершение ребёнка повторяющегося родителя упрощено до boolean; при переносе нужно сохранить ось вхождений и операции core, а не копировать это упрощение.

## Состояния и границы реализации

Сохраняются локальные записи, очередь синхронизации, offline, отказ сервера и Undo. Ошибки и ожидающие записи не скрываются ради визуальной чистоты. Не добавляются команды, AI, напоминания или время выполнения как новые сущности.

Пользователь явно расширил исходное ограничение «только стилизация» до UX-редизайна. Новая навигация, пресеты, раскрытие полей, действия добавления и переключение режима требуют отдельных изменений клиентского поведения. Их необходимо описать в task spec перед переносом, сохраняя URL-контекст, i18n, CSP и осознанно обновляя контракты тестов, если меняются имена или роли контролов.

## Синхронизация с TUI

Оба клиента должны иметь одинаковую продуктовую семантику, адаптированную к своему способу управления. Общий источник поведения — client-core и утверждённые спецификации; HTML-прототип не заменяет их.

Сверено с [TUI client design](../specs/2026-10-03-tui-client-design.md), планами [T2 shell](../plans/2026-10-03-plan-t2-tui-shell.md), [T3a outline](../plans/2026-10-03-plan-t3a-tui-outline.md) и [T3b board](../plans/2026-10-03-plan-t3b-tui-board.md). На момент сверки параллельные worktree: `tui-t0-engine` (engine → core) и `tui-t1-reparent` (общая операция reparent). Эти названия фиксируют контекст, а не факт завершения работ.

### Общие требования

- Один уровень детей: project → task → subtask. Проект пока трактуется как существующая принадлежность задачи, а не новая задача типа epic.
- В outline ребёнок вложен в родителя, когда оба соответствуют фильтру; при отсутствии родителя ребёнок остаётся доступен со ссылкой/префиксом родителя. Сворачивание не меняет данные и не учитывает ребёнка второй раз.
- Прогресс родителя согласован между outline, board и details и обновляется после добавления, завершения и Undo. Нельзя вычислять его только по видимым детям и выдавать за полный прогресс.
- Подзадача имеет свой статус; перенос её карточки не должен неявно менять статус родителя.
- При создании подзадачи сохраняется подстановка проекта родителя; последующие изменения проекта не каскадируются между родителем и ребёнком.
- Scheduled и due — разные даты, без времени; `p0` — самый высокий, `p4` — самый низкий приоритет; грамматика быстрого ввода общая.
- Offline-запись считается принятой локально. Добавление/редактирование закрывает ввод только после `result.ok`; отказ сохраняет текст и показывает причину. Повтор одного намерения не создаёт новую операцию.
- Done, Undo, skip, перенос в завершающую колонку, повторяющиеся вхождения и удаление используют общие операции core, а не независимые клиентские трактовки.
- Reparent должен использовать общий write kind и проверки core. Web не реализует собственную альтернативу через редактирование `parentId`.

### Различия интерфейсов

Web использует иконки режимов справа вверху, drawer, pointer/touch и доступные меню. TUI использует курсор, fold/unfold, горячие клавиши, picker и панель деталей. Одинаковая семантика не требует одинакового расположения контролов, клавиш или библиотеки UI.

### Утверждённые правила переноса (2026-10-03)

Пользователь подтвердил: List/Board — временный выбор текущего контекста, сохранённое представление меняется только явно; фильтр и режим восстанавливаются из URL при reload и Back/Forward; drawer сохраняет контекст и возвращает фокус; раскрытие показывает всех прямых живых детей с обозначением детей вне фильтра без увеличения счётчика; полный прогресс идёт из core по всем детям и соответствующему вхождению. Web и TUI используют одинаковую семантику операций, адаптируя управление.

Спецификация реализации и приёмки: [T-2026-10-03-web-redesign-context](../../specs/tasks/active/T-2026-10-03-web-redesign-context.md). Статус ready означает готовность требований к реализации, а не завершение переноса.

### Технические условия переноса

1. **Layout:** Web использует локальный override в URL; TUI v1 использует сохранённый view.layout. Оба поведения согласованы с текущим TUI spec и не изменяют view молча.
2. **Дети вне фильтра:** `Item.subtasks` уже содержит полный прогресс, `taskDetails` — checklist всех живых детей. При переносе определить чтение дополнительных полей детей через core projections/topics, не подмешивая их в счётчик фильтра и не копируя engine в Web.
3. **Проект ребёнка:** подстановка проекта родителя при создании сохраняется, без последующего каскада изменений проекта. Аналогия Jira не вводит дополнительного запрета другого проекта у ребёнка; такой запрет отдельно не утверждён.
4. **Завершение родителя:** действующий core подтверждает независимое завершение родителя и детей. При переносе сохранить occurrence-aware projections и mark/Undo для повторяющегося родителя; fixture прототипа не проверяет этот случай.

### Порядок координации

Владелец TUI меняет TUI spec/планы и свои worktree; владелец Web proposal меняет этот документ и макеты. Общие операции и projections согласуются до изменения, с одним владельцем каждой правки. Не править чужие активные файлы и не копировать engine в клиент.

Перед интеграцией проверить общий сценарий на одной реплике: создать родителя и ребёнка → увидеть вложенность/связь в двух клиентах → поменять статус ребёнка → проверить прогресс → Undo → отфильтровать родителя → ребёнок остаётся понятным → offline-запись → синхронизация. Дополнительно проверить refused reparent и сохранение введённого текста. Отчёт о передаче требований не равен подтверждению принятия другой стороной.
