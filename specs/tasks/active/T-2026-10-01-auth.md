### Goal

The server stops at `register` and `login` with a 15-minute stateless access
token: no refresh, no logout, no revocation, open registration, and the CLI's
callers mint tokens with curl. A web client cannot ship on that, and an
instance on the internet cannot keep registration open. This task builds the
rest of the auth surface the design settles.

### Scenarios

1. **Given** a signed-in CLI, **When** its access token expires, **Then** the
   next command refreshes it silently and succeeds.
2. **Given** a refresh token that was already rotated more than 30 s ago,
   **When** anyone presents it, **Then** the session is revoked and both
   holders must sign in again.
3. **Given** a refresh whose response was lost, **When** the client retries
   within 30 s with the old token, **Then** it gets the same new pair.
4. **Given** an instance with users, **When** someone registers without an
   invitation, **Then** they are refused; with the owner's invitation they
   succeed once.
5. **Given** a user who forgot their password and no SMTP, **When** the owner
   resets it, **Then** the user's sessions are revoked and the new password
   works.
6. **Given** ten wrong passwords for one address, **When** an eleventh login
   comes, **Then** it is answered 429 with `Retry-After`.

### Requirements

- **FR-001** Sessions MUST be server rows; refresh tokens MUST rotate on every
  refresh and a spent token presented outside the grace window MUST revoke the
  session (← Q2).
- **FR-002** A spent token presented within 30 s of its rotation MUST return
  the same successor pair (← Q4).
- **FR-003** Access tokens MUST live 15 minutes; a session MUST expire 30 days
  after its last refresh and 1 year after sign-in (← Q5).
- **FR-004** `POST /auth/logout` MUST revoke the current session, or every
  session with `{ all: true }`; a password reset or change MUST revoke every
  session (← Q11).
- **FR-005** Registration MUST be open only while the instance has no users;
  the first account becomes the owner; afterwards it MUST require a valid,
  unused, unexpired invitation (single use, 7 days, optional email binding),
  stored as a hash (← Q7, ADR 0014).
- **FR-006** The owner MUST be able to reset another user's password; `forgot`
  MUST say mail is not configured; a host script MUST print a one-time
  15-minute reset code that `POST /auth/reset` accepts (← Q8, Q10).
- **FR-007** `DELETE /auth/account` MUST require the password and purge the
  user's data; the owner MUST be refused while other users exist (← Q9).
- **FR-008** Failed logins MUST be rate-limited per address and per IP, and
  invalid refreshes per IP, answering 429 with `Retry-After` (← Q12).
- **FR-009** Passwords set by register, reset or change MUST have at least 8
  characters including a letter, a digit and a symbol (← Q14).
- **FR-010** `todoer login <email>` MUST read the password from
  `TODOER_PASSWORD` or stdin (no echo on a terminal) and store the tokens in
  the CLI's SQLite; `todoer logout [--all]` MUST revoke and clear them
  (← Q3, Q6, Q13).
- **FR-011** Every CLI command MUST refresh the access token when it expires
  within a minute and once on a 401, serialised across processes by the store;
  `TODOER_TOKEN` MUST still override; resetting the replica MUST NOT clear the
  tokens (← Q4, Q6, Q13).
- **FR-012** The OpenAPI document, README, HELP, ADR 0011 and 0014, the domain
  design §5 and both e2e scripts MUST describe and exercise the new surface
  (← project rules 3 and "spec first").

### Edge cases

- two first registrations racing on an empty instance → exactly one owner
  (FR-005, T006)
- an invitation bound to another email → refused (FR-005, T006)
- refresh with a token of a revoked or expired session → 401, no new pair
  (FR-001, FR-003, T004)
- two server-side refreshes of the same current token at once → one rotation,
  the other gets the grace answer (FR-002, T004)
- `TODOER_TOKEN` set and a stored session present → the env token wins, no
  refresh (FR-011, T007)
- `logout` with no stored session → exit 0, nothing sent (FR-010, T008)
